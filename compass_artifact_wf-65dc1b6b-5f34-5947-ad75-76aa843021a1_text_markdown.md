# Code Knowledge Graph RAG для Python-микросервисов: критический архитектурный анализ (середина 2026)

## TL;DR
- **Ядро проекта здравое, но самая рискованная и недооценённая часть — это symbol resolution (вопрос A), а не чанкинг и не выбор графовой БД.** tree-sitter + LlamaIndex `CodeSplitter` дадут узлы, но CALLS-рёбра между файлами вам придётся строить отдельным инструментом (scip-python на базе Pyright — лучший практичный выбор), и именно тут FastAPI `Depends()`, декораторы и динамическая регистрация хэндлеров дадут пропуски. Закладывайте это как основной источник погрешности.
- **Честное предупреждение: есть реальные доказательства, что хорошо оснащённый агент с grep + LSP может обойти вашу графовую систему по большинству задач.** Claude Code сознательно не индексирует код. Но для вашего конкретного кейса — многосервисные, кросс-async бизнес-процессы KYC — статический граф даёт то, чего grep не даёт: детерминированный multi-hop, который проходит через брокерные границы. Это и есть ваша защищаемая ниша; всё, что можно сделать grep'ом, графом делать не нужно.
- **По хранилищу: не берите KùzuDB (репозиторий заархивирован 10 октября 2025, одновременно с финальным релизом 0.11.3; Apple заключила сделку о покупке Kùzu Inc. 9 октября 2025 согласно EU DMA-филингу).** Для v1 стройте на Postgres (pgvector + рекурсивные CTE), который у вас уже есть; переходите на FalkorDB или Neo4j только когда упрётесь в глубину обхода. Для агента используйте небольшой набор типизированных инструментов, а НЕ raw text-to-Cypher (на CypherBench лучшая модель Claude 3.5 Sonnet даёт лишь 61.58% execution accuracy, GPT-4o — 60.18%).

## Key Findings

1. **Symbol resolution — это отдельная, тяжёлая подсистема, а не свойство tree-sitter.** tree-sitter принципиально не резолвит имена между файлами. Лучший практичный путь для Python — `scip-python` (обёртка над Pyright), дающий точность навигации уровня Pylance/PyCharm. Альтернативы (`pycg`, `code2flow`, Jedi) либо не масштабируются, либо заброшены.
2. **Async-ститчинг producer→consumer из «сырого» Python-кода не решён ни одним готовым инструментом — это ваш кастомный компонент.** Готовая комбинация существует только если сервисы написаны на FastStream (авто-генерация AsyncAPI) + EventCatalog (сшивка по каналам).
3. **Temporal — это подарок для вашей модели.** Workflow-определения Temporal — это уже явные, детерминированные определения бизнес-процессов в коде. Они должны быть first-class узлами-якорями, а не выводиться эвристически.
4. **AST-производный граф бьёт LLM-извлечённый граф по надёжности и стоимости** (arxiv 2601.08773): детерминированный граф строится за секунды против сотен секунд у LLM-подхода, с меньшим числом пропусков.
5. **«Перегрузка CALLS» — реальная и задокументированная ошибка** существующих систем (code-graph-rag/Memgraph): CALLS используют для containment/usage вместо истинного вызова. Не повторяйте.
6. **Выбор графовой БД менее важен, чем кажется.** Для узлов/рёбер уровня одного продукта Postgres достаточно. KùzuDB (казалось бы, идеальный embedded-выбор) заброшена.
7. **Для агента типизированные инструменты надёжнее raw Cypher.** text-to-Cypher ненадёжен (Claude 3.5 Sonnet 61.58%, GPT-4o 60.18% execution accuracy на CypherBench; открытые модели <10B — <20%).
8. **Contextual retrieval (Anthropic) применим к коду и даёт измеримый прирост** — прибавляйте путь файла, родительский класс, импорты, docstring, позицию в графе к чанку перед эмбеддингом.

## Details

### A. Symbol resolution для Python call graph — САМАЯ рискованная часть

Это ядро вашего графа (CALLS-рёбра), и tree-sitter здесь бесполезен: он строит AST одного файла и не резолвит `import`/атрибуты/методы между файлами. Разбор вариантов:

- **scip-python (Sourcegraph, на базе Pyright) — практичный выбор №1.** Переиспользует type-checking и семантический анализ Pyright, даёт стабильные символы (включая кросс-репозиторные ссылки на зависимости). Индексирует в формат SCIP (преемник LSIF). Устанавливается через npm (`@sourcegraph/scip-python`), требует Node 16+, работает с активированным virtualenv, чтобы видеть зависимости. Формат SCIP — protobuf, читается из Python. Минусы: это Node-инструмент (не чистый Python-пайплайн), и есть отчёты о том, что на очень больших/сложных деревьях он «падает и жрёт CPU бесконечно» (кейс Mozilla с WPT-деревом). Статус поддержки самого scip-python скромный — базируйтесь на нём, но заложите риск.
- **Pyright/basedpyright напрямую.** basedpyright — активно поддерживаемый форк с Python-обёрткой; можно дёргать hover/definition/references. Даёт лучшую в классе type inference, но не отдаёт готовый call graph — придётся обходить definition/references самому.
- **Jedi.** Быстрый, чистый Python, встраивается легко, историко хорош для автодополнения; на некоторых кодовых базах быстрее Pyright. Но менее точен на сложном выводе типов и не даёт готового call graph.
- **pycg — state of the art в академии, но непрактичен.** Flow-insensitive межпроцедурный анализ; в бенчмарках не масштабируется — падает по памяти/времени на программах >2000 строк при whole-program анализе, flow-insensitive, не покрывает все динамические фичи Python. **Репозиторий заброшен** («no further development improvements are planned»). Jarvis (демонд-драйвен преемник) существует как научный прототип, но не production-инструмент.
- **code2flow.** Генерирует call graph по эвристике совпадения имён (не по реальному резолву), полезен для визуализации, но неточен для графа-источника-истины.
- **Rope.** Библиотека рефакторинга; имеет резолв, но не предназначена как индексатор call graph.
- **Stack Graphs (GitHub) — важный кандидат, недооценённый.** Rust-реализация (`github/stack-graphs`), на базе tree-sitter, работает в production в GitHub с ноября 2021 для Python на каждом коммите (per Creager et al., «Stack Graphs: Name resolution at scale», arXiv 2211.01224: *«Stack graphs have been running in production since November 2021, analyzing every commit to every public and private Python repository hosted on GitHub»*; GA precise code navigation анонсирована 9 декабря 2021). Ключевое свойство: **file-incremental** name resolution — каждый файл анализируется изолированно, что идеально для инкрементальной переиндексации (вопрос G). Хранит подграфы в SQLite. Есть `tree-sitter-stack-graphs-python`. Минусы: экосистема на Rust (у вас Rust — вторичный язык, но это шанс), покрытие правил для Python зрелее, чем для других языков, но всё ещё требует освоения TSG DSL. Sub-100ms навигация.

**Как ломаются все эти инструменты именно на вашем стеке:**
- **FastAPI `Depends()`.** Даже статические type-checkers (mypy, pyright) не выводят тип, возвращаемый из `Depends(dependency)` — он стирается в `Any` (открытый issue FastAPI #4750). Значит, ребро «эндпоинт → внедрённая зависимость → её вызовы» статически НЕ прослеживается стандартными средствами. Вам придётся написать FastAPI-специфичный экстрактор: парсить аргумент внутри `Depends(...)` / `Annotated[T, Depends(...)]` и добавлять явное ребро. Это кастомный код.
- **Декораторы.** Pyright теряет сигнатуры при некоторых декораторах (issue #774). Роут-декораторы (`@app.get`, `@router.post`) — это как раз ваши якоря; их надо обрабатывать спец-паттернами, а не полагаться на общий резолвер.
- **Динамический диспатч / duck typing.** Фундаментальная граница статики. Ребро «интерфейс → конкретная реализация» будет неполным. Помечайте такие рёбра как `resolution: static|dynamic|heuristic` с уровнем уверенности.
- **Динамически регистрируемые хэндлеры** (реестры плагинов, `add_route()` в цикле, декоратор-регистраторы). Статически часто не видны — здесь опциональные трейсы OTel (вопрос E) особенно ценны для валидации.

**Вывод по A:** используйте scip-python как основной резолвер CALLS; напишите FastAPI/декораторный адаптер поверх; помечайте рёбра уровнем уверенности; рассмотрите Stack Graphs, если инкрементальность станет критичной.

### B. Async / event-driven ститчинг рёбер

**Главный вывод: готового инструмента, который статически парсит «сырой» Python broker-код (kafka-python, aiokafka, confluent-kafka, pika, NATS, Redis streams), извлекает имена топиков и из producer, и из consumer, и сшивает их producer→consumer по общему имени — НЕ существует. Это ваш кастомный компонент.** Авторитетный обзор static-analysis инструментов восстановления архитектуры микросервисов (arxiv 2412.08352, перечисляет 13 инструментов) не содержит ни одного Python-специфичного инструмента для брокерных потоков — почти все Java-ориентированы и REST-центричны (напр. Code2DFD анализирует Java, хотя сам написан на Python).

Что существует и как это использовать:
- **AsyncAPI как формат промежуточного представления рёбер — да, это правильный якорь.** В AsyncAPI Kafka-топик моделируется как «channel», producer/consumer — как publish/subscribe операции. Сшивка сервисов по общему имени канала — стандартный приём.
- **FastStream (`ag2ai/faststream`, production-stable, активен в 2025).** Если (и только если) сервисы используют его декораторы `@broker.subscriber("topic")` и `@broker.publisher("topic")`, он авто-генерирует AsyncAPI 3.0/2.6 через интроспекцию декорированных хэндлеров (`faststream docs serve module:app`). Важное ограничение: работает ТОЛЬКО для FastStream-кода (не для сырого aiokafka), и это runtime-интроспекция объекта приложения, а не чистый AST-парсинг. Простой `broker.publish()` без publisher-объекта в AsyncAPI НЕ документируется.
- **EventCatalog (`event-catalog/eventcatalog`, ~2.8k звёзд, активен, релизы SDK до июня 2025).** Именно он делает кросс-сервисную сшивку: принимает несколько AsyncAPI-документов через плагин `@eventcatalog/generator-asyncapi` и строит producer→consumer карту по общим каналам. Отвечает на «кто публикует OrderCreated?». Есть отслеживание изменений архитектуры между git-ветками.

**Рекомендуемый паттерн для B:** написать AST-экстрактор на Python `ast`, который распознаёт вызовы `producer.send("...")`, `consumer.subscribe([...])`, декораторы `@broker.subscriber(...)` и извлекает строковые литералы имён топиков → эмитить AsyncAPI на сервис → сшивать в графе по имени канала (модель EventCatalog как референс). Проблема: имена топиков часто не строковые литералы, а переменные/константы/f-строки из конфига — здесь потребуется частичный резолв констант, и часть рёбер останется эвристической. Помечайте уверенность.

- **Temporal — используйте его явность.** В отличие от Kafka/broker-кода, Temporal workflow-определения — это уже явные, детерминированные, кодифицированные определения бизнес-процессов в коде. Workflow orchestrates activities явными вызовами (`workflow.execute_activity`). Это **упрощает**, а не усложняет вашу задачу: делайте Workflow-определение first-class узлом типа `BusinessProcess`/`ProcessRoot`, а `execute_activity`-вызовы — явными рёбрами INVOKES_ACTIVITY. Это надёжнее, чем реконструировать процесс из async-брокерных рёбер. Для KYC (где Temporal у вас уже в стеке) это, вероятно, самый надёжный якорь бизнес-процесса из всех.

### C. Схема графа

Наблюдаемые в практике схемы:
- **code-graph-rag (`vitali87/code-graph-rag`).** Узлы: Project/Package/Folder/Module/Class/Function; рёбра CONTAINS_MODULE, CALLS, и др. Хранит в Memgraph, работает как MCP-сервер для Claude Code. Известная слабость (документирована в разборе gdotv по Memgraph): **перегрузка CALLS** — часть рёбер CALLS на самом деле означает containment/usage, а не истинный вызов, плюс «orphan»-узлы (427 orphan Method-узлов в кейсе Soufflé). Прямой урок: не сваливайте containment и invocation в одно ребро.
- **FalkorDB CodeGraph.** Узлы Module/Class/Function/аргументы/переменные; рёбра CALLS, INHERITS_FROM, DEPENDS_ON. «Богаче плоского call graph».
- **GRACE (arxiv 2509.05980, ICSE'26).** Многоуровневый мульти-семантический граф: file structure + AST + function call graph + class hierarchy + data flow graph. Ключевая идея — не терять структуру при подаче в LLM: сериализовать подграф с явными структурными маркерами, а не «наивной конкатенацией».
- **Reliable Graph-RAG (arxiv 2601.08773).** Прямое подтверждение вашего подхода: детерминированный AST-граф (tree-sitter + двунаправленный обход) против LLM-извлечённого. DKB строит граф за секунды (2.81s Shopizer), LLM-KB — сотни секунд (200s+) и пропускает 377 файлов на Shopizer. DKB даёт наивысшую корректность на архитектурных multi-hop вопросах; vector-only хуже всех и с наибольшим риском галлюцинаций.
- **Stack Graphs / Glean (Meta) / Sourcegraph.** Промышленные схемы с явным разделением definition/reference/scope-узлов — референс того, как правильно НЕ смешивать семантику рёбер.

**Рекомендуемая схема для вас:**
- Узлы: `Module`, `Class`, `Function`, `RouteHandler`, `MessageConsumer`, `MessageProducer`, `CronJob`, `CLICommand`, `TemporalWorkflow`, `TemporalActivity`, `Topic/Channel`, `Service`, `BusinessProcess` (кросс-сервисный якорь).
- Рёбра (строго различать семантику!): `CONTAINS` (containment), `CALLS` (ТОЛЬКО истинный синхронный вызов), `HANDLES` (route→handler), `DEPENDS_ON` (FastAPI DI), `PRODUCES`/`CONSUMES` (код→Topic), `INVOKES_ACTIVITY` (Temporal), `PART_OF_PROCESS` (сегмент→процесс), `NEXT_SEGMENT` (сшивка сегментов через async-границу).
- На каждом ребре: `resolution ∈ {static, dynamic, heuristic, trace_validated}` и `confidence`.
- Чанк-payload узла (из `CodeSplitter`) храните как свойство узла + отдельный эмбеддинг.

### D. Хранилище графа

- **KùzuDB — ИСКЛЮЧИТЬ.** Была бы идеальным embedded-выбором (in-process, Cypher, встроенный vector index, Python API), НО проект **заброшен**: репозиторий заархивирован 10 октября 2025 (одновременно с финальным релизом 0.11.3); Apple заключила сделку о покупке Kùzu Inc. 9 октября 2025 (по данным EU DMA-филинга). Форки (LadybugDB) без корпоративного бэкинга. Не стройте новую систему на этом.
- **Postgres (pgvector + рекурсивные CTE, опц. Apache AGE) — рекомендация для v1.** У вас уже есть Postgres в стеке (KYC). pgvector даёт co-location эмбеддингов. Рёбра как таблица `(source_id, target_id, type, resolution, confidence)`; обход — `WITH RECURSIVE` с ограничением глубины и cycle detection. На вашем масштабе (узлы/рёбра одного продукта, не миллионы) recursive CTE на глубину 2–3 отрабатывает за единицы-десятки мс. Apache AGE (openCypher внутри Postgres) — опция, но: хранит в heap-таблицах с B-tree на каждый hop (не index-free adjacency), untyped-результаты из Cypher-строк, и требует компиляции расширения (эксплуатационная морока на разных архитектурах). Многие команды сознательно отвергают AGE в пользу голых CTE. **Начните с голого Postgres+CTE; добавляйте AGE только если Cypher-выразительность реально понадобится.**
- **FalkorDB — первый апгрейд, если Postgres упрётся.** Redis-модуль, in-memory, GraphBLAS/матричный движок, встроенный HNSW vector index в одном движке (гибридный retrieval «вектор + обход» в одном запросе), Cypher, `docker compose up -d`, лёгок в Kubernetes рядом с кэшем. Заявлен как заточенный под inference-time retrieval для GraphRAG/агентов. Портируемость Cypher с Neo4j «в высоких 80–низких 90%». Хорош, когда обход в горячем пути запроса.
- **Neo4j — если нужна экосистема.** Native property graph, index-free adjacency, зрелые GDS/Bloom/APOC, native vector index, Bolt + официальный Python-драйвер. Оправдан при бюджете на enterprise-тулинг и глубоких обходах на больших данных. Для одного инженера, вероятно, избыточен операционно в v1.
- **Memgraph.** In-memory, Cypher, native Kafka ingestion, используется в code-graph-rag. Разумная альтернатива FalkorDB.

**Вердикт D:** Postgres+pgvector+CTE для v1 (нулевая новая инфраструктура, ACID, co-location с вашими KYC-данными) → FalkorDB, когда глубина/латентность обхода станет узким местом.

### E. Агентная навигация по графу + честный контр-аргумент

**Сначала жёсткая правда (пользователь просил pushback):** есть весомые свидетельства, что хорошо оснащённый агент с grep + LSP обходит графовые системы на многих задачах кода.
- Claude Code **сознательно не индексирует** код — только agentic grep + чтение файлов + LSP поверх. Аргумент: индекс устаревает, «кодовая база и есть индекс», нет staleness.
- Промышленный консенсус — **слоистый retrieval**: grep для широкого дешёвого поиска, LSP для точечного символьного подтверждения.
- Amazon Science (arXiv 2602.23368) сообщает, что keyword-поиск через agentic tool use достигает >90% производительности RAG без векторной БД; для кода exact-match часто бьёт семантику на стабильных, хорошо именованных базах.
- Даже symbol-graph индексы (Kythe/Glean/Sourcegraph) в FAANG — это НЕ vector RAG, а именно граф; но их не ставят как backbone для LLM-агентов, потому что «агент, который может грепнуть 30 раз за сессию», окупает индекс хуже.

**Где ваш граф всё же выигрывает (защищаемая ниша):**
- Детерминированный **multi-hop через async-границы** (route→handler→produce→[Kafka]→consume→activity в ДРУГОМ сервисе). grep этого не сшивает — имена топиков и хэндлеров не совпадают лексически, и переход между репозиториями grep не делает.
- **Кросс-сервисные бизнес-процессы KYC** — именно тот класс архитектурных multi-hop вопросов, где vector-only и grep проваливаются (подтверждено 2601.08773).
- **Стабильный, инспектируемый источник истины** для процесса, который можно валидировать трейсами.

**Дизайн интерфейса для агента — вывод: типизированные инструменты, НЕ raw Cypher.**
- **Не давайте агенту генерировать Cypher.** text-to-Cypher ненадёжен: на CypherBench (arXiv 2412.18702, megagonlabs) лучшая модель Claude 3.5 Sonnet даёт лишь 61.58% execution accuracy, GPT-4o — 60.18%, а открытые модели <10B — <20% (*«the highest-performing open-source model reaches only 41.87%... smaller models in the <10B parameter range achieve less than 20%»*). Направление ребра инвертирует смысл, свойства узлов/рёбер в разных namespace. Это неприемлемо для источника истины по KYC.
- **Давайте небольшой набор типизированных инструментов** (ваш вариант b): `find_entrypoint(query)` (vector-поиск якоря), `expand_neighbors(node_id, edge_types, depth)`, `get_source(node_id)`, `trace_process(entrypoint_id)` (сборка полного кросс-сервисного процесса). Это curated, предсказуемо, тестируемо.
- **MCP-сервер** — правильная упаковка этих инструментов (code-graph-rag уже экспонирует ~10 инструментов как MCP для Claude Code; это проверенный паттерн). Оберните ваши типизированные инструменты в MCP.
- Practical hybrid: `find_entrypoint` (вектор) → `trace_process`/`expand_neighbors` (граф) → `get_source` (детерминированное чтение). Дайте агенту и grep как fallback — он всё равно им воспользуется.

### F. Оценка

Разделяйте оценку на три уровня:
1. **Качество графа (самое важное и чаще всего пропускаемое).** Стройте ground-truth call graph на небольшом наборе сервисов (можно динамически, трассировкой исполнения тестов, или ручной разметкой) и меряйте **precision/recall рёбер CALLS/PRODUCES/CONSUMES**. Отдельно — доля orphan-узлов и доля рёбер с `resolution=heuristic`. Разбор gdotv прямо показывает: сначала система построения графа, потом языковая; слабая модель может скрыть сильный граф и наоборот.
2. **Retrieval.** Precision@K / Recall@K на золотом наборе «вопрос → релевантные узлы». Для кросс-файлового/репо-уровня используйте установившиеся бенчмарки как основу методологии: **RepoBench** (в т.ч. RepoBench-R для retrieval, Python+Java; метрики EM/ES/CodeBLEU), **CrossCodeEval** (кросс-файловое дополнение, cross-file зависимости через статику), CodeSearchNet (устаревает, но базовый). SWE-bench — для end-to-end агентных задач, если пойдёте туда.
3. **Generation / end-to-end.** Соберите **свой золотой набор из ~15 архитектурных/трейсинговых вопросов на репозиторий** — ровно методология 2601.08773 (те же 15 вопросов на всех пайплайнах, разные под каждую базу). Меряйте корректность ответов и hallucination rate, сравнивая три ветки: vector-only, ваш граф, grep+LSP-агент. Это и есть ваш честный тест «стоило ли строить граф».

Метрики графа против ground-truth важнее retrieval-метрик: если рёбра неверны, всё сверху бесполезно.

### G. Инкрементальная индексация / staleness

- **Staleness — это реальный аргумент ПРОТИВ индекса** (главный довод Claude Code). Смягчается инкрементальностью.
- **tree-sitter даёт инкрементальный парсинг** из коробки (это его дизайн-цель).
- **Паттерн на git diff.** На каждый коммит: определить изменённые файлы, перепарсить только их, инвалидировать/пересобрать узлы и рёбра, инцидентные этим файлам. Проблема — «island»: CALLS-ребро зависит от другого файла. code-graph-rag честно признаёт, что их realtime-updater **пересчитывает ВСЕ CALLS-рёбра на каждое изменение файла** ради консистентности (потенциальная проблема производительности на больших базах) — не копируйте это наивно.
- **Stack Graphs — эталон инкрементальности.** File-incremental by design: подграф каждого файла строится изолированно и переиспользуется, если файл не менялся (Merkle-tree по содержимому blob). Именно поэтому GitHub гоняет их на каждый коммит всех Python-репозиториев. Если инкрементальность станет критичной — это сильнейший аргумент взять Stack Graphs как слой резолва.
- **Практический совет:** храните хэш содержимого каждого файла; рёбра, чей source/target файл не изменился и чьи зависимости не изменились, не пересчитывайте. Кросс-файловые CALLS инвалидируйте по множеству затронутых символов, а не «все всегда».

### H. Контекстная аугментация чанков

Anthropic Contextual Retrieval даёт измеримый прирост и **явно тестировался в т.ч. на кодовых базах**. По первоисточнику Anthropic («Contextual Retrieval in AI Systems»): Contextual Embeddings + Contextual BM25 снижают частоту неудачных retrieval (top-20) на 49% (с 5.7% до 2.9%), а с добавлением reranking — на 67% (с 5.7% до 1.9%). Одни только contextual embeddings дают ~35% сокращение неудач (5.7%→3.7%); в Claude Cookbook на 9 кодовых базах Pass@10 вырос примерно с 87% до 95%.

Для кода конкретно прибавляйте к чанку перед эмбеддингом:
- Путь файла и имя модуля.
- Родительский класс/функцию (сигнатуру внешней области).
- Релевантные импорты (что вызывается).
- Docstring функции/класса.
- **Позицию в графе** — уникально для вас: имя якорного бизнес-процесса, сервис, тип узла, входящие/исходящие типы рёбер. Это ваш «graph-aware contextual retrieval».
- Гибрид с BM25 (точные совпадения имён символов — коду критично, т.к. имена точны).
- cAST (EMNLP 2025) — структурный чанкинг через AST — подтверждает, что AST-границы чанков (то, что делает `CodeSplitter`) — правильная база.

Используйте prompt caching, чтобы генерация контекста для чанков не была дорогой (прогоняйте весь файл-родитель как кэшированный контекст).

### Замечание про CodeSplitter
`CodeSplitter` (LlamaIndex, на базе tree-sitter, подход SweepAI: жадное слияние sibling AST-узлов до max-size) — валидный выбор ядра чанкинга. Параметры: `language`, `chunk_lines`, `chunk_lines_overlap`, `max_chars`. Требует `tree-sitter` + `tree-sitter-language-pack`. Есть Rust-порт (`wangxj03/code-splitter`) — если захотите перенести горячий путь на Rust. Держите чанки привязанными к узлам графа по стабильному ID (файл + span). Оверлап между чанками осмысленно отключить/минимизировать, раз границы совпадают с AST-узлами и у вас есть граф для контекста.

## Recommendations

**Этап 0 — MVP-срез (докажите ценность до постройки всего):**
1. Возьмите 2–3 реальных KYC-сервиса. Постройте золотой набор из ~15 кросс-сервисных архитектурных вопросов.
2. Прогоните базовую линию: agentic grep + LSP (basedpyright) и vector-only RAG. Зафиксируйте их результаты. **Это ваш бар.** Если граф его не побьёт на multi-hop — пересмотрите объём проекта.

**Этап 1 — Статическое ядро (стандартный граф без async):**
3. `CodeSplitter` → узлы; `scip-python` → CALLS-рёбра. Напишите FastAPI-адаптер (`Depends`, роут-декораторы) и пометку `resolution/confidence` на рёбрах.
4. Хранилище: Postgres + pgvector + рекурсивные CTE. Схема узлов/рёбер из раздела C, со строгим разделением CONTAINS vs CALLS.
5. Якоря процессов: RouteHandler, MessageConsumer, CronJob, CLICommand, **TemporalWorkflow** (first-class).
6. Агент: 4 типизированных инструмента (`find_entrypoint`, `expand_neighbors`, `get_source`, `trace_process`) через MCP. **Никакого raw Cypher.**

**Этап 2 — Async-ститчинг (ваша дифференцирующая ниша):**
7. Кастомный AST-экстрактор топиков (producer/consumer) → PRODUCES/CONSUMES → Topic-узлы → NEXT_SEGMENT через границу. Temporal `execute_activity` → INVOKES_ACTIVITY. Используйте AsyncAPI как промежуточный формат; EventCatalog-модель как референс сшивки.
8. Пометьте heuristic-рёбра там, где имя топика не строковый литерал.

**Этап 3 — Обогащение и эксплуатация:**
9. Graph-aware contextual retrieval (раздел H) + BM25-гибрид.
10. Опциональные OTel/Jaeger-трейсы: повышайте `confidence` рёбер до `trace_validated`, добавляйте динамически-обнаруженные рёбра, невидимые статике.
11. Инкрементальная переиндексация по git diff + хэши файлов; при росте базы — оцените Stack Graphs для file-incremental резолва.

**Пороги для смены решений:**
- Обход глубины >3–4 или латентность CTE >100ms на горячем пути → мигрируйте на FalkorDB.
- Доля `resolution=heuristic` рёбер >~20% на CALLS → усильте резолвер (перейдите с эвристики на scip/Stack Graphs), иначе граф не источник истины.
- Если agentic grep+LSP бьёт граф на вашем 15-вопросном наборе → не расширяйте граф, вкладывайтесь в инструменты агента.
- Переиндексация коммита >неск. секунд → внедряйте Stack Graphs / file-incremental.

## Caveats
- **Symbol resolution — главный источник ошибок и объём кастомной работы.** Ни один инструмент не даст 100% точный Python call graph; FastAPI DI, декораторы, duck typing и динамическая регистрация гарантируют пропуски. Проектируйте систему так, чтобы она была полезна при неполном графе (уверенность на рёбрах, fallback на grep у агента).
- **Async-ститчинг из сырого кода — не решён индустрией; это кастом.** Строковые литералы топиков — счастливый случай; конфиг-переменные/f-строки потребуют частичного резолва констант и оставят эвристические рёбра.
- **Экосистема нестабильна:** KùzuDB заброшена (окт 2025); pycg заброшен; scip-python поддерживается скромно; Stack Graphs — Rust с неравномерным покрытием языков. Закладывайте риск сопровождения зависимостей.
- **Реальный риск, что проект не окупится против grep+LSP-агента.** Стройте MVP-срез (Этап 0) прежде, чем инвестировать в полный граф. Ваша защищаемая ценность узкая, но реальная: детерминированные кросс-async, кросс-сервисные KYC-процессы.
- **Числа из некоторых источников — маркетинговые** (бенчмарки FalkorDB против Neo4j публикует сам FalkorDB; «10x быстрее grep» — от вендоров vector-поиска). Проверяйте на своих данных.
- **arxiv 2601.08773 и GRACE — на Java/на code-completion соответственно**, не на вашем точном кейсе (Python, KYC, агент). Направление выводов переносится, конкретные числа — нет.
