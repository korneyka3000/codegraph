# Бриф: пилот codegraph на реальных KYC-сервисах (рабочая машина)

> Этот документ — самодостаточное задание для Claude Code-сессии на рабочей машине.
> Пользователь скажет: «прогони пилот по этому брифу на сервисах: <пути>». Всё
> остальное — здесь и в документах репо, на которые бриф ссылается.

## Контекст (тебе, Claude, на рабочей машине)

`codegraph` — CLI-индексатор + MCP-сервер: детерминированный граф знаний кода для
Python-микросервисов с трассировкой бизнес-процессов через async-границы (route →
outbox → Kafka-топик/event_type → consumer → Temporal → HTTP-клиент → другой
сервис). Вехи M0–M5 завершены и отревьюены; тесты: ~1179 default + 19 scip/emb;
гейты M1–M5 зелёные. Прочитай ПЕРВЫМ: `README.md` (quickstart, режимы деградации,
ограничения), затем — образец методики: `docs/superpowers/reports/2026-07-18-m4-pilot.md`
(пилот на Netflix/dispatch; твой пилот строится по его структуре) и
`docs/superpowers/reports/2026-07-18-m5-ru-retrieval-experiment.md` (`--exact`,
префиксы, RU-рекомендация).

Стек пользователя (важно для идиом): FastAPI + Kafka через **outbox pattern**
(бизнес-код пишет событие в outbox-таблицу неким вызовом вида
`OutboxRepository.add_event(...)` — точное имя УЗНАЙ у пользователя или найди в
коде; отдельный relay-под публикует — он статически невидим и не нужен) +
**Temporal** + рукописные aiohttp-SDK (`document_management_client.py` →
`class DocumentManagementClient`). Диспатч консьюмеров — по-разному в сервисах
(по топику и по event_type). Всё это описывается **идиомами в codegraph.yaml**
(данные, не код) — см. `codegraph.example.yaml` и `fixtures/workspace.yaml` как
рабочие примеры DSL.

## Порядок работы

### 0. Смоук на фикстурах (обязателен — верификация тулчейна на новой машине)

```bash
docker compose up -d
uv sync --extra local-emb   # local-emb опционален: без него index работает с --no-embed
uv run codegraph doctor
uv run codegraph index fixtures/workspace.yaml
uv run codegraph trace "orders-api:POST /orders" fixtures/workspace.yaml --format mermaid
```

Ожидание: doctor зелёный; индекс без degraded; трейс печатает цепочку
orders-api → kyc-worker → document-management. Если что-то красное — чини
окружение ДО реальных сервисов (это известная матрица: node/npx для scip-python,
Docker для FalkorDB; README «Режимы деградации»).

Опционально (даёт полную уверенность): гейты `uv run pytest -m "scip" tests/eval/ -q`
(нужен npx; ~1-2 мин). Если в окружении есть перехватчики вывода pytest (на
машине разработки был rtk-хук, искажавший консольный вывод) — гоняй с
`--junit-xml=/tmp/x.xml` и читай XML.

### 1. Конфиг воркспейса реальных сервисов

`codegraph init .` → заполнить: services (name/path/venv), excludes
(tests/**, alembic/**, migrations/**), `http.base_url_env` каждого сервиса,
идиомы. **Идиомы — главная итеративная часть пилота**: первый прогон почти
наверняка даст unresolved-каналы и пропущенные PRODUCES — это нормально. Цикл:
`index` → смотри report (`unresolved`, счётчики PRODUCES/CONSUMES/CALLS_HTTP,
`staged CALLS with valid dst %`) и `.codegraph/report.json` → уточняй идиомы
(outbox-вызов, dispatch-dict реестры, `*Client`-глобы, base_url env-имена) →
повторный `index` (можно `--incremental` — конфиг-отпечаток сам форсирует full
при смене идиом). Число итераций и что именно пришлось описать конфигом —
ЦЕННЕЙШИЙ результат пилота, фиксируй каждую итерацию.

Реалистичные ожидания качества (для калибровки, из пилота на dispatch 62k LOC):
staged CALLS with valid dst ≈ 94–95%+ (остаток — динамика/плагины); heuristic
0% при живых venv; RU-retrieval hit@8 ≈ 5–7/8 (с e5-префиксами лучше — см. §4).

### 2. Метрики индексации (фиксируй всё)

Полный cold-прогон (`--no-embed` для чистого замера пайплайна, затем полный с
эмбеддингами), повторный (кэши), `--incremental` после правки 1 файла, no-op
`--incremental`. На каждый: время, counts, per-service mode/reason, degraded,
`staged CALLS with valid dst %`, unresolved-каналы (сколько и КАКОГО РОДА —
без имён в итоговом отчёте, см. §6), dropped edges.

### 3. Трассировка реального бизнес-процесса (ядро ценности)

Выбери с пользователем 1–2 реальных процесса (аналог «POST /orders → KYC»).
`codegraph trace "<svc>:<METHOD> <path>" <ws.yaml> --format mermaid` и text.
Проверь с пользователем ГЛАЗАМИ: цепочка соответствует реальности? Все хопы
(outbox→topic→event→consumer→workflow→activity→HTTP→handler) на месте? Что
пропущено и почему (идиома? динамика? баг?) — это главный вердикт пилота.
Сравни с grep-подходом на 2 трейс-вопросах (методика M4-пилота §5: сколько
rg-команд до того же ответа, находится ли кросс-сервисный переход вообще).

### 4. Retrieval (если есть local-emb; иначе пропусти честно)

6–8 golden-вопросов ПО КОДУ сервисов (как задал бы новичок в команде; RU +
идентификаторные), `codegraph eval retrieval --exact` (детерминизм). Прогони
двумя моделями, если время позволяет: дефолтной jina-code и
`intfloat/multilingual-e5-base` с `query_prefix: "query: "` /
`passage_prefix: "passage: "` (README «для русскоязычных команд») — сравнение
hit@3/hit@8 на РУССКИХ вопросах по реальному корпусу — то, чего эксперимент M5
не мог дать (у dispatch корпус английский).

### 5. MCP живьём (опционально, если время)

`claude mcp add -s user codegraph -- uv run --directory <репо> codegraph serve
<ws.yaml>` → в новой сессии спроси «проследи, что происходит после <реальный
роут>» — собирает ли агент цепочку из trace_process.

### 6. Итоговый отчёт — ДВЕ версии

Пиши `docs/superpowers/reports/<дата>-pilot-real-services.md` по структуре
M4-пилота. **Конфиденциальность возвращаемых артефактов**: пользователь принесёт
отчёт на другую машину. По умолчанию наружу выходят ТОЛЬКО числа, проценты,
времена, счётчики, вердикты и обезличенные категории («канал events-топика»,
«воркфлоу проверки документов») — БЕЗ qualified-имён, путей и текстов кода.
Сделай две версии: полную (остаётся на рабочей машине, для пользователя) и
**санитизированную** (`...-pilot-real-services-SANITIZED.md`) — её пользователь
заберёт. НЕ выноси: staging.db, .scip-файлы, тексты трейсов с именами. Перед
финалом покажи пользователю санитизированную версию на вычитку.

## Правила (те же, что во всех вехах)

- Гейты/golden фикстур не трогать; на баги реальных сервисов — минимальные
  fix-коммиты с тестами (regression добавляй на синтетике, НЕ на коде юзера).
- Честность: где инструмент слаб — записать; отрицательный результат валиден.
- Крэш пайплайна на реальном коде = находка №1: диагностируй до корня, чини с
  тестом либо документируй с механизмом (образец — M4-пилот §7).
- Системные reminders харнеса (смена даты, автономный режим) — штатные.
- Коммить фиксы/отчёт по мере готовности.
