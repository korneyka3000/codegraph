# M5 T6 — RU-retrieval эксперимент: jina-embeddings-v2-base-code vs intfloat/multilingual-e5-base (exact mode)

> Методология: `.superpowers/sdd/task-6-brief.md`. Честность превыше маркетинга --
> тот же принцип, что у M4 T10 pilot report: если e5 не выигрывает, это фиксируется
> как есть, а не сглаживается.

## 1. Постановка

M4 T10 pilot (`docs/superpowers/reports/2026-07-18-m4-pilot.md`, §4.2) нашёл, что
чисто-русские концептуальные вопросы (без буквального совпадения идентификатора)
проседают у дефолтного эмбеддера `jinaai/jina-embeddings-v2-base-code` -- гипотеза
там: код-специализированная модель слабее на абстрактной русскоязычной семантике,
чем настоящая multilingual-модель была бы. Этот эксперимент проверяет гипотезу
напрямую: переиндексировать тот же пилотный граф (Netflix/dispatch, те же 8
golden-вопросов) моделью `intfloat/multilingual-e5-base` (multilingual, НЕ
код-специализированная, с канонической query/passage-инструкцией) и сравнить
hit@3/hit@8 в детерминированном (`--exact`) режиме.

## 2. Методология

**Стенд:** тот же пилотный клон и golden-вопросы, что M4 T10 (`Netflix/dispatch`,
commit `dd2837e82a0bf5565b1b4b4b91ea30b7262d4061`, 493 файла в scope после
excludes, единственный сервис `dispatch`, 8 вопросов -- микс чисто-русских
концептуальных, EN-идентификаторов и RU+идентификатор, см.
`docs/superpowers/reports/2026-07-18-m4-pilot.md` §1/§4). Клон и
`.codegraph/scip/`-кэш (content-addressed по `tree_hash`) пережили M4 в
scratchpad-директории сессии и переиспользованы как есть -- без повторного
клонирования или scip-анализа с нуля.

**Staging пересоздан, не переиспользован.** Унаследованный от M4
`.codegraph/staging.db` был на `schema_version=5`; текущий код требует
`SCHEMA_VERSION=6` (`core/schema.py`) -- несовместимо
(`Staging._check_schema_version_before_ddl` падает громко на мисматче, миграции
нет). Файл (плюс `-wal`/`-shm`) удалён, `.codegraph/scip/`-кэш оставлен (не
завязан на `staging.db`) -- следующий `codegraph index` пересоздал `staging.db`
на v6 и переиспользовал тёплый scip-кэш (S1-S6 заняли секунды, не ~48с
холодных, см. M4 §3.2), но `Staging.embedding_cache` (таблица ВНУТРИ
`staging.db`, ключ `(input_hash, embed_model)`) пропала вместе с файлом.
Следствие, зафиксированное честно: **jina тоже переэмбежена с нуля в этом
прогоне, не только e5** -- оба числа ниже получены полным `embedded_fresh`
эмбеддингом, ни одно не подогрето чужим кэшем.

**Один граф, строгий порядок.** Обе модели -- `provider: local`, тот же
`codegraph index` пайплайн; смена модели -- правка `embedding:` в pilot
`workspace.yaml` между двумя прогонами. Граф (`pilot_dispatch`, FalkorDB)
перезаписывается blue/green-свопом при каждом `index`, поэтому: jina прогнана,
проиндексирована и **измерена первой** (пока граф ещё jina-эмбеженный), только
потом конфиг переключён на e5 и переиндексирован. `workspace.yaml` и
`workspace.jina-backup.yaml` (исходный конфиг) лежат рядом в pilot-директории.

**Метрика:** `codegraph eval retrieval <workspace> --questions questions.yaml
--k 8 --exact`. Один прогон с `--k 8` даёт per-question rank (0-based, "-" если
ответ вне top-8), из которого hit@3 (rank < 3) и hit@8 (rank < 8, т.е. просто
"hit" при k=8) читаются оба, без отдельного `--k 3` прогона -- rank уже несёт
всю нужную информацию. `--exact` (M5 T2) -- полный детерминированный Cypher-скан
(`vec.cosineDistance`), не ANN -- убирает несидированный HNSW-шум, задокументированный
в M4 §4.1 как источник ±1-2 вопросов разброса МЕЖДУ идентичными прогонами
одной и той же модели; M4's собственные ANN-числа поэтому несравнимы напрямую с
числами ниже (другой метод измерения, не только другая модель).

**Детерминизм проверен эмпирически, не только заявлен**: каждая модель
прогнана `eval retrieval --exact --k 8` дважды подряд (без переиндексации между
прогонами) -- байтовое сравнение (`diff`) обоих выводов.

## 3. Baseline: `jinaai/jina-embeddings-v2-base-code` (M0-дефолт)

Конфиг (без изменений от M4, только staging пересоздан):
```yaml
embedding: { provider: local, model: jinaai/jina-embeddings-v2-base-code }
```

`codegraph index`: полный ре-эмбед (staging пересоздан, см. §2) -- `chunks =
3271 (embedded: 3271 fresh + 0 cached, reused: 0)`, wall-clock 5м51с
(17:11:34 → 17:17:25; практически совпадает с M4's собственным первым
прогоном на этой же модели, 5м36с S8 + прочие стадии = 5м51с итого -- ожидаемо,
тот же холодный embedding-кэш, тот же CPU). Модель -- 768-мерная.

`codegraph eval retrieval --exact --k 8`, 2 прогона: **байт-в-байт идентичны**
(`diff` -- пусто, ~8-9с на прогон, доминирует загрузка модели, не сам скан).

| # | вопрос | rank (k=8) | hit@3 | hit@8 |
|---|---|---|---|---|
| 1 | где создаётся новый инцидент (RU) | - | MISS | MISS |
| 2 | как рассчитывается стоимость реагирования на инцидент (RU) | - | MISS | MISS |
| 3 | engage_signal_identity function signal engagement (EN id) | 0 | **HIT** | **HIT** |
| 4 | где создаётся тикет в Jira для инцидента (RU) | 4 | MISS | **HIT** |
| 5 | assign_role_flow назначение роли участнику инцидента commander scribe (mixed) | 0 | **HIT** | **HIT** |
| 6 | кто вызывает отправку уведомлений участникам notification service send (RU, trace #1) | 7 | MISS | **HIT** |
| 7 | что происходит после создания инцидента какие ресурсы создаются автоматически (RU, trace #2) | - | MISS | MISS |
| 8 | где определяется приоритет инцидента по имени get_by_name_or_default (RU+id) | 4 | MISS | **HIT** |

**hit@3 = 2/8 (25%). hit@8 = 5/8 (62.5%).** По всем 8 рангам совпадает с M4's
исходным ANN-снимком «сразу после эмбеддинга» -- совпадение НЕ гарантировано в
общем случае (exact и ANN могут расходиться), но граф здесь небольшой, а снимок
M4 был снят до пересборок индекса, так что близость правдоподобна; это не
проверялось как общее свойство и не нужно проверять для целей этого эксперимента
(exact -- источник истины здесь, ANN упомянут только для контекста).

## 4. Contender: `intfloat/multilingual-e5-base` + канонические query/passage-префиксы

задачи, `provider: local` -- единственный провайдер, который их читает):
```yaml
embedding: { provider: local, model: intfloat/multilingual-e5-base, query_prefix: "query: ", passage_prefix: "passage: " }
```

`codegraph index`: полный ре-эмбед (новая модель -- 100% cache miss в

объяснение -- меньшая модель/иная архитектура forward-пасса, не измерялось

## 5. Сравнение

| # | вопрос | jina rank | e5 rank | hit@3: jina→e5 | hit@8: jina→e5 |
|---|---|---|---|---|---|
| 1 | где создаётся новый инцидент (RU) | - | - | MISS→MISS | MISS→MISS |
| 2 | стоимость реагирования (RU) | - | 4 | MISS→MISS | MISS→**HIT** |
| 3 | engage_signal_identity (EN id) | 0 | 0 | HIT→HIT | HIT→HIT |
| 4 | тикет в Jira (RU) | 4 | 1 | MISS→**HIT** | HIT→HIT |
| 5 | assign_role_flow (mixed) | 0 | 5 | HIT→**MISS** | HIT→HIT |
| 6 | кто вызывает уведомления (RU, trace #1) | 7 | 4 | MISS→MISS | HIT→HIT |
| 7 | что происходит после создания (RU, trace #2) | - | 7 | MISS→MISS | MISS→**HIT** |
| 8 | приоритет по get_by_name_or_default (RU+id) | 4 | 0 | MISS→**HIT** | HIT→HIT |
| | **итого** | | | **2/8 → 3/8** | **5/8 → 7/8** |

Не универсальный выигрыш -- честно видно и регресс: **Q5 хуже с e5** (rank0 →
rank5 -- всё ещё hit@8, но больше не hit@3). Чистый эффект тем не менее заметно
положительный: **+1 вопрос на hit@3, +2 вопроса на hit@8**, причём выигрыш
сосредоточен именно там, где M4's диагностика (§4.2) предсказывала слабость
jina -- чисто-русские концептуальные вопросы без буквального ID-пересечения (Q2,
Q7 оба перевернулись из MISS в HIT). Q1 -- единственный вопрос, MISS у ОБЕИХ
моделей даже на k=8 (топ-1 e5 -- код из другого домена, `plugins.dispatch_jira`)
-- не решено переключением модели, честно зафиксировано как остаточное
ограничение, не скрыто.

## 6. Вывод

Правило из плана: e5 ≥ +2 вопроса на hit@8 относительно jina (5/8) -- триггерит
README-рекомендацию «для русскоязычных команд» (конфиг-сниппет, БЕЗ смены
дефолта). **Порог достигнут ровно** (+2, 5/8 → 7/8) -- рекомендация добавлена
(см. README «Ограничения», рядом с существующей заметкой про RU-fulltext).

Формулировка выигрыша, без переоценки: n=8 вопросов на ОДНОМ пилотном репозитории
(Netflix/dispatch, Python/FastAPI) -- статистически это анекдотический, не
строгий результат (нет доверительных интервалов, нет второго репозитория/домена
для проверки переноса). Но направление согласуется с независимой диагностикой
M4 (§4.2: "слабое качество русскоязычной семантики у jina-embeddings-v2-base-code
именно для абстрактных концептуальных формулировок") и с ожидаемым свойством
моделей: `jina-embeddings-v2-base-code` обучена и специализирована на
код-релевантных (в основном англоязычных) корпусах, `multilingual-e5-base` --
на explicitly multilingual retrieval-задачах с canonical query/passage
инструкциями -- ровно то различие, которое и должно было бы объяснить именно
такой сдвиг (выигрыш на чисто-концептуальных RU-вопросах, паритет на
идентификатор-содержащих). Рекомендация в README -- opt-in для команд с
преимущественно русскоязычными concept-вопросами, не универсальная замена
дефолта: jina остаётся код-специализированной моделью и может выигрывать на
других осях, которые этот эксперимент не измерял (английские идентификаторные
запросы, скорость и т.д.), а на идентификатор-содержащих вопросах ЭТОГО
эксперимента она как минимум не хуже e5 (Q3 -- точный паритет, оба rank0) и
местами лучше (Q5 -- jina rank0 против e5 rank5, единственный чистый регресс
из §5).
