## 1. Итерации идиом

**Одна итерация**: сверка конвенций с кодом → конфиг → рабочий индекс с первого прогона.
Описано конфигом (данные, не код): decorator-SDK для HTTP-клиентов (маршрут из декоратора,
verb из enum-конструктора запроса, вызов через driver-метод), base_class-consumer (event_type
из generic-параметра базового класса), producer-обёртка. Ключевая находка итерации: **FQN
базового класса консьюмера различается по сервисам** — два сервиса наследуют shared-базу
напрямую, оркестратор — через локальную обёртку над алиас-импортом той же базы (плюс
mixin-первый порядок базовых классов); base_class-идиом настраивается по-сервисно.

## 3. Дельта vs baseline и трасс-вердикт

| Ребро | Baseline | Re-run |
|---|---|---|
| Temporal activity | 0 | **64** |
| HTTP-вызов | 0 | **44** |
| CONSUMES | 0 | **16** |
| NEXT_SEGMENT | 0 | **3** |
| Temporal start-mark | 4 | **7** |
| event-каналы | 0 | **15** |
| PRODUCES | 0 | 0 (динамический топик — честно) |

Каналы по типу: HTTP-роут 135 / event-type 15 / kafka-topic 1.

**Трасс-вердикт (главный). Смешанный.** Внутрисервисные Temporal-леги (workflow-менеджер →
activity) корректны — 64 ребра static/1.0. Но кросс-сервисный HTTP-хоп, хоть и материализуется
ребром, **резолвится неверно**: механизм создаёт claim с точным путём, а таргетинг без env-якоря
мислинкует (см. оговорку 1).

**Честные оговорки:**

1. **Кросс-сервисный HTTP резолвится ЛОЖНО без env-пиннинга base_url.** Клиенты берут хост из
   динамического атрибута (не env), поэтому линковка матчит по форме пути поперёк всех сервисов
   без target-якоря: **3 из 44 «резолвнутых» — ложные** (три несвязанных клиент-метода с разными
   верными путями схлопнулись на один роут другого сервиса; у канала даже service пуст),
   41 — без матча. Корректных кросс-хопов = 0. Решение (идея пользователя): целевой сервис
   HTTP-ручки детерминированно извлекается из Helm-чартов (env `SERVICE_*_URL` → DNS-хост → имя
   сервиса) + валидация формы пути в рамках целевого сервиса. Механизм создания claim'ов работает;
   таргетинг — открытая доработка.
2. **Temporal activity 64, не ~80** (~78%): остаток — вызовы, где ссылка на активность идёт через
   переменную/фабрику или вне просканированного scope. Честный потолок статики, не регресс.
3. **NEXT_SEGMENT — только HTTP (3), Kafka event-пар = 0.** Producer оркестратора публикует с
   динамическим топиком → канала нет; в пределах среза множества produced-событий и
   consumed-событий **не пересекаются** (реальные контрагенты вне среза). Свойство среза, не
   механизма — механизм доказан синтетическим M6-гейтом на fixture-стеке.
4. **verb-миссы = 15**: один из сервисов использует подкласс класса-запроса и альтернативный
   driver-метод, не покрытые единичным `request_ctor`. Честный видимый мисс, уточняемо — в бэклог.

## 4. Вывод

**Частично.** Три из пяти gap'ов **подтверждены закрытыми и корректными**: Temporal activity
0→64, CONSUMES 0→16 (оба static/1.0), start-marks 4→7 — верны; within-service граф без регрессий
(valid dst 91.3%, unresolved 4.9%, degraded=0); миссы стали видимы. Но **три остаточные проблемы
открыты** (отдельный backlog-документ): (R1) кросс-сервисный HTTP-таргетинг без env-якоря даёт
ложные рёбра — решается извлечением target из Helm; (R2) Producer с динамическим топиком
(PRODUCES=0) — нужен enum/event_type-якорь; (R3) Temporal signals не покрыты вообще (34 хендлера
+ 45 отправок) — крупный невидимый пласт orchestration-трассировки. Механизмы M6 (activity/
consumer) работают; HTTP-лег, producer и сигналы требуют доработки.
