## 3. ГЛАВНЫЙ вердикт — полная трасса целевого сценария

**Собирается.** Целевой сценарий проекта — «событие → обработчик-события → сигнал →
обработчик-сигнала» с ветвлением в кросс-сервисный HTTP — **впервые материализуется как явные
переходы сегментов в одном трейсе**. Структура (обезличенная):

```
S0 (Обработчик события), сервис-оркестратор
   ├─ канал HTTP (композитный путь /api/vN/...) → маршрут ДРУГОГО сервиса   ← HTTP-хоп, кросс-сервис
   ├─ канал сигнала (typed) → два обработчика-сигнала                        ← сигнальный хоп
   └─ канал HTTP → unresolved                                               ← внешний сервис, честно
S1 (Обработчик маршрута), внутренний сервис-адресат   ← HTTP-хоп приземлился в чужом сервисе
S2 (Обработчик сигнала), сервис-оркестратор
S3 (Обработчик сигнала), сервис-оркестратор
```

Оба ключевых НОВЫХ хопа — явные переходы сегментов:
- **HTTP-хоп**: `HTTP-вызов static/1.0 → роут-канал → HANDLES`; путь **композитный**, собран
  транзитивно через файлы (R4 закрыт); сегмент-адресат — реальный обработчик маршрута другого сервиса.
- **Сигнальный хоп**: `PRODUCES static/1.0 → сигнал-канал → CONSUMES`; типизированная ссылка на
  метод резолвнута в обработчики-воркфлоу (R5 закрыт).

Проверено ещё на трёх входах — паттерн стабилен. NEXT_SEGMENT: 23 HTTP-пары (клиент→маршрут
другого сервиса) + 20 сигнал-пар (отправитель→обработчик), все static/1.0.

**Дисклеймер честности:** в этом трейсе за обработчиком-сигнала не следует activity→HTTP
(обработчики кладут данные в очередь воркфлоу — реактивная часть вне синхронной цепочки
вызовов). Но оба ранее рвавшихся звена — typed-сигнал и композитно-путевой кросс-сервисный
HTTP — теперь явные, корректные, static/1.0. Трасс-уровневый confidence 0.50 отражает наличие
heuristic/0.5 внешних HTTP-каналов, а не слабость резолвнутых хопов (те — 1.0).
