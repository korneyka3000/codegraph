## 4. Что агент понял бы неверно / чего не хватило (вход для M10)

1. **hit@8 = 5/8 — гранулярность чанков, не деградация модели.** Большие классы режутся на N
   чанков, часть которых делит один qualified_name = имя класса; строгая метрика по qualified_name
   тогда хрупка (sibling-чанки перебивают целевой метод). Предложение: search_code должен отдавать
   enclosing-символ и различать class-/method-level чанки.
2. **Разбор 3 промахов (accept не расширял).** Два — правильный КЛАСС в top-1, но метод-чанк
   перебит sibling'ами того же класса (см. п.1). Третий — клиент-vs-сервер неоднозначность запроса
   (доминирует клиентская сторона); единственный «настоящий» промах. Предложение: подсказывать
   агенту service-фильтр для «где обрабатывается» (сервер) vs «кто вызывает» (клиент).
3. **who_calls не покрывает вызовы-через-активность.** Для Temporal-активности «кто вызывает» — это
   отдельный тип ребра; who_calls вернул 0 и агент может решить «мёртвый код». Предложение: для
   узлов-активностей опционально включать источники по этому ребру.

## 5. Диагностика dropped-рёбер (беклог-вопрос)

**149 dropped CALLS.** Топ-префикс — **79 (53%)** это вызовы метода через **модульный
синглтон-инстанс** (`name = Class(...)` на уровне модуля; `name.method()`): dst резолвится в
`module.attr`, реального метода класса под таким id нет → ребро дропается (счётный паттерн в двух
consumer-сервисах). Это **не dispatch-плагины**. Остальное — методы на модель/event-инстансах и
несколько локальных переменных (динамика, честно). Предложение M10: джойнить
`<module-level-name>.<method>()` к методу класса типа инстанса (тип известен из assign в том же
модуле — тот же приём, что уже применяется для Settings-полей). Закрыло бы ~53% dropped одним
паттерном.
