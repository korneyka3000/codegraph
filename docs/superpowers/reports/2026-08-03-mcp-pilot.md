## 4. Что агент понял бы неверно / чего не хватило в инструментах (вход для M10)

### 4.1. hit@8 = 5/8 — не деградация модели, а гранулярность чанков

Большие классы (`DocumentStorageClient`, `ServicesSettings`, `VerificationRequestsClient`) режутся
на N чанков, часть которых **делит один qualified_name = имя класса** (различаются лишь `##cN` в
chunk_id). Строгий hit@k по `(service, qualified_name)` тогда хрупок: sibling-чанки того же класса
перебивают целевой метод-чанк. **M10-предложение**: в ответе search_code отдавать
`enclosing_symbol` + различать class-level и method-level чанки, чтобы (а) агент видел, какой
именно метод, (б) метрика не штрафовалась за «правильный класс, не тот под-чанк».

### 4.2. Разбор 3 промахов (accept НЕ расширял — anti-curve-fit)

- **«загрузка файла в хранилище»**: top-1..8 — все `DocumentStorageClient` (правильный класс!), но
  целевой метод-чанк `upload_file_for_document` перебит sibling-чанками того же класса. Практически
  — попадание; строго — MISS из-за §4.1.
- **«конфигурация адресов сервисов по URL»**: top-1 = `ServicesSettings.validate_cross_service_urls`
  — **тот самый класс** `ServicesSettings`, но метод-чанк, а accept назвал bare-class → строгий MISS
  при фактически верном top-1. Тоже §4.1.
- **«добавление связанных клиентов v2»**: top-1..8 — `VerificationRequestsClient` (**клиентская**
  сторона в camunda), а accept назвал **серверный** хендлер в vr. Реальная клиент-vs-сервер
  неоднозначность запроса; клиентские методы доминируют эмбеддингами. Единственный «настоящий»
  retrieval-промах из трёх. **M10-предложение**: `service`-фильтр в search_code уже есть — агенту
  стоит подсказывать его для «где ОБРАБАТЫВАЕТСЯ» (сервер) vs «кто ВЫЗЫВАЕТ» (клиент).

### 4.3. who_calls не покрывает INVOKES_ACTIVITY

Для Temporal-активности «кто вызывает» через `execute_activity_method` — это ребро INVOKES_ACTIVITY,
а who_calls ходит только по CALLS → вернул 0. Агент, спросивший «кто вызывает эту активность»,
получит пустоту и может решить «мёртвый код». **M10-предложение**: для узлов с ролью
TemporalActivity who_calls опционально включать INVOKES_ACTIVITY-источники (trace_process уже это
моделирует).

## 5. Диагностика dropped CALLS (беклог-вопрос §5 брифа)

**149 dropped CALLS**; топ-префиксы dst:

| N | dst-префикс | природа |
|---|---|---|
| **79** | `app.db.registry.session` | **модульный синглтон-инстанс** |
| 13 | `app.kyc_engine.models.*` | методы на модель-инстансах/классах |
| 10 | `app.db.events.*` | то же (event-фабрики) |
| 6 | `app.models.notification.*` | то же |
| ~30 | прочие (models/events) + несколько `localN` | локальные переменные (динамика, честно) |

**Главная находка (53% dropped).** `registry = _DBRegistry(config.database.dsn)`
(`app/db/registry.py:58`) — **модульный синглтон**; вызовы `async with registry.session() as …`
(79 сайтов в vr:44 + dm:35) резолвятся в dst `app.db.registry.session` (module.attr), но реальный
метод — `_DBRegistry.session`, и узла под таким id нет → ребро дропается. Это **не dispatch-плагины**,
а нерезолвинг метода, вызванного через module-level instance singleton. **M10-предложение**: джойнить
`<module-level-name>.<method>()` к методу класса типа этого инстанса (тип известен из assign
`name = ClassName(...)` в том же модуле — тот же приём, что M7 class-attr harvesting уже использует
для Settings-полей). Закрыло бы ~53% dropped одним паттерном.

module-level-singleton method-calls (закрыл бы 53% dropped CALLS). Live-LLM-сессия поверх MCP —
доступна пользователю (сервер зарегистрирован), в этом прогоне проверен инструментальный слой.
