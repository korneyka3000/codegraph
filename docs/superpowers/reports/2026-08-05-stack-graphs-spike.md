Более дешёвая и менее рискованная альтернатива для того же порога (§7) —
не смена резолвера, а смена МОДЕЛИ ВЫЗОВА уже используемого scip-python
(batch CLI → долгоживущий процесс/`--watch`, тот же pyright-движок под капотом).

## 1. Контекст и вопрос

Порог #3 мастер-плана (`docs/superpowers/specs/2026-07-12-codegraph-design.md:272`):
«Переиндексация коммита > нескольких секунд после M4 → рассмотреть stack-graphs».
Порог сработал в M4: пилот на реальном сервисе (Netflix/dispatch, 493 файла,
62 177 строк) показал **57.05s на правку ОДНОГО файла через `--incremental`**
— **100.5% от full-cold (56.78s)**, т.е. де-факто без выигрыша
(`docs/superpowers/reports/2026-07-18-m4-pilot.md` §6). Причина задокументирована
там же: `ScipRunner` кэширует по merkle-hash ВСЕГО дерева сервиса — любое
изменение файла инвалидирует кэш целиком, `scip-python` перегоняет весь сервис
заново (~83% времени прогона на этом масштабе). Частичная инкрементальность M4
(T5/T6: узкий stale-набор для S5/S6/S8) экономит только оставшиеся ~17%, что
тонет в шуме на 493-файловом сервисе.

`SymbolResolver` как формальный `Protocol`-класс (`resolvers: name, resolve() ->
ResolveResult` с `iter_defs()/iter_refs()`) существует только в исходной спеке
(`docs/superpowers/specs/2026-07-12-codegraph-design.md:157-160`) — **в реализации
его нет** (`grep -rn "SymbolResolver"` по `src/` — ноль совпадений). Реальная
поверхность — два свободных модуля, каждый строящий `list[DefRow]`/`list[RefRow]`
(`resolvers/base.py`): (a) `resolvers/scip/{runner,reader}.py` — реальный SCIP;
(b) `resolvers/fallback.py::resolve_service` — эвристический деградированный
путь. Это не мелочь для оценки объёма интеграции — см. §6.

### 3.3. Запросы definition — честные результаты

CLI даёт только `query definition PATH:LINE:COL...` (1-based; можно батчить
несколько позиций в одном вызове) — **bulk-дампа всех occurrences, как у SCIP
Index-протобуфа, нет вообще**, и `query references` (обратный резолв) — тоже
нет ни одной команды под это (`query -h` → только `definition`).

| запрос | ожидание | результат |
|---|---|---|
| `DocumentService` в `from app.services.documents import DocumentService` (routes/documents.py:4) | кросс-файловый класс | **резолвится чисто**, 1 def → `services/documents.py:1:7 class DocumentService` |
| `service.fetch(doc_id)` (routes/documents.py:12) — атрибутный вызов на локально сконструированном инстансе | атрибут/метод на объекте без аннотации типа | **резолвится чисто**, 1 def → `DocumentService.fetch` (byte-точно) |
| `service.store(payload)` (routes/documents.py:18) | то же | **резолвится чисто**, 1 def → `DocumentService.store` |
| `emit_document_indexed(...)` вызов (routes/documents.py:19) — импортированное имя | кросс-файловая функция | резолвится, **но** «found 2 definitions for **2 references**» — см. 3.4 |
| `DocumentService()` конструктор (routes/documents.py:11) | то же | тот же «2 references» паттерн |
| `APIRouter` из `fastapi` (routes/documents.py:1) | third-party, venv не подключён | честный **0 definitions** — не резолвится, и не должен (нет venv/site-packages awareness у тула вообще) |

Атрибутный резолв (`service.fetch`/`.store`) — это ровно тот кейс, который
бриф задания называл главным подозреваемым на провал («stack graphs'
name-binding model vs Python's dynamic attribute semantics»). На этой
фикстуре он **отработал корректно и точно** — честный положительный результат,
не подтверждающий a priori опасение.

### 3.4. Странность формата вывода — «2 references» на одну позицию

Для ссылок, ведущих ЧЕРЕЗ `from X import Y` (использование импортированного
имени, не прямой атрибутный доступ), `query definition` на одной и той же
byte-позиции матчит **два** внутренних reference-узла: один — «has no
definitions» (мёртвый), второй — «has 2 definitions», где среди двух
«определений» — САМА строка импорта (`from app.events.producer import
emit_document_indexed`) **и** настоящее определение в файле-источнике. Прямой
атрибутный доступ (`service.fetch`) такого раздвоения не даёт — там ровно
1 reference / 1 definition. Для адаптера это значит: нужна дедупликация по
позиции + правило выбора «не импорт-рестейтмент, а настоящее определение» —
недокументированная деталь формата, которую пришлось откалибровать вручную.

### 3.5. Инкремент — механизм подтверждён

На копии фикстуры (не на трекнутой — `fixture-copy/`, чтобы не трогать репо):
правка ОДНОГО файла из 8 (`producer.py`), повторный `index` **без `-f`**:

```
app/__init__.py: cached index
app/events/__init__.py: cached index
app/events/producer.py: indexed        ← только этот
app/main.py: cached index
app/routes/__init__.py: cached index
app/routes/documents.py: cached index
app/services/__init__.py: cached index
app/services/documents.py: cached index
```

**Файл-инкрементальность подтверждена буквально** — контент-хэш гейтит
перевычисление НА УРОВНЕ ФАЙЛА, а не всего дерева (в отличие от
`ScipRunner`'а merkle-hash-по-всему-дереву — корень 100.5%-провала M4 §6).

### 3.6. Корректность инкремента — доказано, не предположено

Критичный тест: сдвинул определение `emit_document_indexed` в `producer.py`
на 8 строк (16→24, вставкой блока комментариев), переиндексировал (только
`producer.py` пересчитан, `documents.py` остался «cached index» — НЕ
тронут), затем **повторно запросил ТУ ЖЕ позицию** в `documents.py:19:11`
(файл, который не переиндексировался):

```
has 2 definitions
   .../documents.py:3:33   (импорт-рестейтмент)
   .../producer.py:24:11   ← НОВАЯ строка, а не старая 16
```

Кросс-файловый резолв корректно подхватил сдвиг **без переиндексации
файла-потребителя** — это именно та lazy path-stitching модель, которую
заявляет теория stack graphs (граф каждого файла строится локально и
независимо; резолв — это стежка графов НА МОМЕНТ ЗАПРОСА, а не кэшируемый
заранее результат). На этой фикстуре предположение подтвердилось
экспериментально, не только в теории.

## 4. Coverage vs SCIP на той же фикстуре

Базовая линия — `fixtures/.codegraph/staging.db`, свежий (`sha256` файлов на
диске совпадает с `files`-таблицей), реальный прогон `scip-python 0.6.6`:
**29 defs / 58 refs** для `document-management`.

stack-graphs на той же фикстуре (по прямым запросам, не полный дамп — тула
для дампа нет, см. 3.3) резолвит корректно ровно те позиции, что были
проверены точечно (кросс-файловые классы/функции, атрибуты локальных
инстансов) — **но** структурно не резолвит две категории, которые SCIP на
этой же фикстуре резолвит:

- **stdlib/builtins** — SCIP даёт `scip-python python python-stdlib 3.11
  builtins/str#` и `builtins/dict#` для аннотаций типов (`str`, `dict` в
  сигнатурах); у stack-graphs `builtins.py` пуст (§2.2) — такого нет вообще.
- **third-party (`fastapi`)** — SCIP резолвит `fastapi/__init__:` через venv
  сервиса; stack-graphs честно возвращает 0 definitions (нет
  venv/site-packages awareness ни в CLI, ни в архитектуре тула).

Итог: на **прямом пересечении** (first-party defs/refs внутри сервиса)
результаты SCIP и stack-graphs совпали там, где я сверил (не исчерпывающе —
фикстура маленькая, полного bulk-сравнения инструмент не даёт). За пределами
first-party stack-graphs строго беднее SCIP на этой фикстуре.

## 5. Интеграционная оценка

### 5.1. Формы вывода принципиально разные

SCIP: **непрозрачная строка глобального символа** (`scip-python python
<pkg> <ver> <descriptors>` / `local N`), самодостаточная — `symbols.py::
parse_symbol` + `ids.py::node_id` строят canonical id ИЗ САМОЙ СТРОКИ, без
обращения к позиции определения. Вся грамматика этих descriptor-строк
(`` `mod`/Class#method(). ``, параметр-теги вида `(cls)`, `local N`) —
**зашита в `core/ids.py`, `resolvers/scip/symbols.py` и, глубже всего, в
`extractors/calls.py`** (`_is_callable_descriptor` проверяет
`.endswith("().")`; `_cls_construction_dst` — regex по `(cls)`-хвосту;
first-party-vs-external различается членством в `def_symbols_set` — множестве
СТРОК). `ids.py`'шный докстринг прямо формулирует дизайн-инвариант: «id,
построенный экстрактором структурно, равен id, выведенному из SCIP-символа».

stack-graphs: **позиция определения** (`file:line:col`), никакой глобальной
строки-идентификатора не существует в принципе. Это не «тот же протокол,
другой бэкенд» — это другая форма результата.

### 5.2. Что маппится чисто, что — нет

**Чисто маппится:**
- `class_attrs.py` (pydantic-Settings/Enum харвестинг) — целиком на стороне
  tree-sitter `FileFacts`, резолвера не касается вообще; подтверждено чтением
  модуля — неважно, какой резолвер выбран.
- Сама генерация `DefRow` — можно строить из tree-sitter `FileFacts`
  структурно (`fallback.py` уже это делает для деградированного пути,
  готовый прецедент).
- Байтовые спаны определений — совпадают по духу (оба источника дают точные
  диапазоны имени).

**Не маппится без работы:**
- `RefRow.symbol` (SCIP-строка) — у stack-graphs эквивалента нет; нужен
  ЛИБО (A) переход `calls.py`/`symbols.py` на резолв по позициям (полностью
  байпасит descriptor-грамматику, но требует переписать
  `_is_callable_descriptor`/`_cls_construction_dst`/local-vs-external
  логику — заново, под новую форму данных, без готовых аналогов), ЛИБО
  (B) синтез ПОДДЕЛЬНЫХ scip-shaped строк из результата stack-graphs +
  собственного позиционного индекса дефов (тот же приём, что уже применяет
  `fallback.py` для эвристического пути — оставляет `calls.py` нетронутым,
  но всё равно требует построить service-wide (file, byte) → id индекс с
  нуля, плюс разрулить дедупликацию «2 references» из §3.4).
- Bulk-экстракция — SCIP отдаёт весь `Index`-протобуф разом (`reader.py`);
  у stack-graphs нужно САМИМ прогнать tree-sitter, собрать байтовые позиции
  всех call/name-сайтов, сконвертировать байты→line:col (обратная задача
  к тому, что `spans.py::LineIndex` уже решает для SCIP UTF-16, но не тот
  же код), батчем скормить в `query definition`, распарсить вывод. Работает
  архитектурно (тот же subprocess-паттерн, что уже у `ScipRunner`), но это
  новый пласт кода, не переиспользование существующего.
- Типов нет ни у кого в API `SymbolResolver`-протоколе сегодня — не потеря.
- Уровень деградации/confidence — новой строки в нормативной таблице
  resolution/confidence (`design.md` §«Нормативная таблица») сегодня нет;
  потребуется отдельное дизайн-решение (static/1.0 при более бедном
  покрытии, чем сегодняшний SCIP-путь? новый именованный tier?).

### 5.3. Оценка объёма

Не «заменить один модуль» — **вариант (B)** (дешевле, сохраняет `calls.py`):
ориентировочно **2–3 недели** на первый рабочий проход (subprocess-обвязка,
byte↔line:col конвертер, service-wide позиционный индекс дефов, дедуп
«2 references», синтез scip-shaped строк) — и это ДО отдельного хардненинг-
хвоста: `calls.py`'шный докстринг документирует, что аналогичная
SCIP-специфичная логика прошла минимум три отдельных раунда ревью-фиксов
(M5 Bug B — third-party маскировка под first-party; M10 — module-singleton
редирект; M11 — classmethod `(cls)`-конструкция) — у нового пути будут СВОИ
edge case'ы (декораторы вообще не моделируются грамматикой, §2.2), и их
предстоит открывать заново. **Вариант (A)** (нативный позиционный join,
`calls.py` переписывается) — оценочно дороже, **4–6+ недель**, потому что
теряется весь накопленный набор регрессионных фиксов, специфичных для
descriptor-строк.

## 6. Риски

1. **Апстрим мёртв** (§2.1) — любой найденный дефект (включая уже известные
   пробелы: декораторы, builtins, third-party) чинить некому; единственный
   путь — форк и самостоятельная поддержка `.tsg`-грамматики (Rust +
   собственный DSL, отдельная компетенция, которой в проекте сегодня
   нигде нет).
2. **Не тонкий адаптер, а частичный rewrite** (§5) — `calls.py`/`symbols.py`/
   `ids.py` несут накопленную, многократно рецензированную логику,
   завязанную на форму SCIP-строк; свап резолвера не изолирован
   `SymbolResolver`-протоколом настолько чисто, насколько предполагал
   дизайн M0 (протокола как класса в реализации вообще нет, см. §1).
3. **Coverage regression** на builtins/stdlib и third-party (§4) —
   объективно беднее сегодняшнего SCIP-пути, не только «другой формат».
4. **Формат вывода с сюрпризами** (§3.4) — недокументированное раздвоение
   references для импорт-цепочек; спайк откалибровал это вручную путём
   проб, не по документации (её просто нет на таком уровне детализации).
5. **Маленькая экосистема** — единственный сторонний Python-биндинг,
   найденный в поиске (`nohehf/stack-graphs-python-bindings`), — 10 звёзд,
   неофициальный; страховки на случай проблем с самим Rust-crate
   практически нет.

Контр-баланс (честно, чтобы вердикт не читался предвзято): установка простая,
инкремент — реальный и доказанный, а не рекламный (§3.5–3.6), и ключевое
опасение брифа (атрибутный резолв) на практике не подтвердилось на
проверенных кейсах.

## 7. Альтернативы

**Приоритетная (рекомендуется как следующий шаг ВМЕСТО stack-graphs):**
смена модели инвокации уже используемого `scip-python`, не резолвера.
`ScipRunner` сегодня — batch CLI (`scip-python index . --output <file>`),
одноразовый процесс на весь S3. Но `scip-python` — тонкая обёртка над
`pyright` («very few changes... primarily just exposing internal functions»,
по собственному блогу Sourcegraph), а у `pyright` есть штатный `--watch`
режим с быстрым инкрементальным перечекингом на долгоживущем процессе. Корень
проблемы M4 — не «SCIP как формат» и не «pyright не умеет в инкремент», а
конкретно **batch-инвокация текущего `ScipRunner`**, выбрасывающая тёплое
состояние между прогонами. Если завести `scip-python`/`pyright` как
долгоживущий процесс с `didChange`-подобной инвалидацией, есть шанс закрыть
порог #3 **без единой строчки изменений** в `calls.py`/`symbols.py`/`ids.py`
— несравнимо меньший и менее рискованный периметр, чем вариант (A)/(B) §5.3.
Это отдельный спайк по объёму сопоставимый с текущим, но с явно более
дешёвым best-case.

**Прочее, короче:**
- **basedpyright** — активный community-форк pyright; при проблемах с самим
  pyright (а не с моделью инвокации) — путь отступления для движка под
  scip-python-подобной обвязкой. Статус поддержки не проверялся глубоко в
  рамках этого спайка (не было времени по таймбоксу) — если приоритетная
  альтернатива всё же упрётся в проблему самого pyright, стоит отдельно
  свериться.
- **Astral `ty`** — Rust, с нуля, incremental-by-design (файл-до-функции
  гранулярность, salsa-подобная архитектура — та же техника, что у
  rust-analyzer), тот же коллектив, что `ruff`/`uv`. По состоянию на 2026 —
  **beta, 1.0 таргетится «в течение 2026»** (не вышла на момент спайка).
  Явно самый credible долгосрочный кандидат в экосистеме — быстрее
  развивается, лучше профинансирован, чем что-либо в orbit stack-graphs —
  но сегодня не готова к продакшену; кандидат на СЛЕДУЮЩИЙ спайк, не на
  немедленное действие.
- **Статус-кво** — текущая частичная инкрементальность M4 (skip
  неизменившегося сервиса — работает и экономит по-настоящему; узкий
  stale-набор для S5/S6/S8 внутри изменившегося сервиса) уже
  задокументирована и принята как честное архитектурное ограничение
  (`m4-pilot.md` §6, §8) — не блокер сегодня, просто не «секунды».

## 8. Рекомендация

**NO-GO на стек-graphs сейчас; LATER с условиями пересмотра ниже.**
Следующий практический шаг — не этот спайк, а отдельный (меньший по
периметру) спайк «`scip-python`/`pyright` в режиме долгоживущего процесса»
(§7) — он метит в тот же порог #3 заметно дешевле и без риска частичного
rewrite `calls.py`.

**Условия пересмотра stack-graphs** (любое из):
1. `github/stack-graphs` (или адекватно ресурсный форк) выходит из
   архивации / появляется реально поддерживаемая ветка, закрывающая
   builtins/decorators/third-party пробелы (§2.2, §4) и продолжающая
   релизиться выше 0.3.0.
2. Приоритетная альтернатива (§7, watch-режим scip-python/pyright) отдельно
   исследована и **не** дотягивает до «секунд» — тогда stack-graphs
   возвращается в рассмотрение как запасной вариант, а не первый выбор.
3. Реальный масштаб codegraph вырастает настолько, что сегодняшнее принятое
   ограничение (57s/правка на 493-файловом сервисе, `m4-pilot.md`) реально
   мешает пользователю на практике, а не остаётся теоретическим
   недостатком.
4. Astral `ty` (или сравнимый по темпу проект) выходит в стабильный релиз с
   потребляемым codegraph выводом (SCIP-совместимым или легко адаптируемым)
   — при её темпе разработки это может обогнать stack-graphs как решение
   того же порога с более здоровым апстримом.
5. В команде находится ресурс на постоянную поддержку форка
   `.tsg`-грамматики (Rust + собственный DSL) — предпосылка, без которой
   вариант «форкнуть и доделать» из README самого stack-graphs не
   реалистичен.

## 9. Ограничения этого спайка (честно)

- Фикстура (`document_management`, 8 файлов) **на порядки меньше** реального
  сервиса из M4-пилота (493 файла/62k LOC) — таймы §3.5 показывают МЕХАНИЗМ
  (файл-гейтинг, корректная кросс-файловая рестежка), но НЕ являются
  измерением на том же масштабе, что 57s-число из M4; экстраполяция на
  реальный масштаб не проводилась (нет доступа к тому же внешнему репо
  в рамках этого спайка).
- Проверка ограничена точечными `query definition` вызовами (тула для
  bulk-дампа нет, §3.3) — не исчерпывающее сравнение defs/refs, как в
  таблице §4, а точечная сверка выбранных позиций.
- Более сложные Python-паттерны из реальных сервисов (декораторы фреймворков,
  `self.attr`-паттерны с наследованием, dispatch-словари, замыкания) на этой
  фикстуре не встречаются — вывод о decorator/builtins-пробелах опирается на
  анализ исходников грамматики (§2.2), не на прямой hands-on провал на
  фикстуре (фикстура для этого просто не годится по составу).
- `basedpyright` не проверялся hands-on в рамках таймбокса (см. §7).
